gog-tabs / gog-tab

Tabs

A tablist over projected <gog-tab> children. Each tab declares its own header text, icon and disabled state, so a tab is defined in exactly one place rather than split between a header array and a content block.

Overview

Import both components and nest them.

activeIndex is two-way and gogTabChange reports each change. A disabled tab is skipped by the arrow keys and cannot be chosen.

Examples

Sizes and tab states

A tab is active, inactive or disabled; every tablist here holds one of each. A tab is disabled through its own disabled input. Hover, focus and press are pseudo-class states a page cannot force; the headers are live.

Alignment

Where the headers sit in the row. stretch shares the row between them; the other three keep each header its natural width.

Icons

iconName on a gog-tab adds a leading icon to the default header. It is aria-hidden: the label names the tab.

Custom headers

A gogTabHeader template replaces every header button's content, with the gog-tab itself as $implicit and active, disabled and index beside it. It renders inside the tab's button, so it must not hold another control.

Vertical

The headers stack beside the panel, and ArrowUp / ArrowDown move between them instead of left and right.

Overflowing headers

Headers that do not fit scroll inside a gog-scroll rather than a native scrollbar — the one piece of chrome no --gog-* token can reach. With scrollActiveIntoView on (the default) choosing a tab centres it — instantly on first render and under prefers-reduced-motion, smoothly otherwise — and the track is hidden. The second row turns it off and gets a track, since then it is the only hint there is more to reach; showScrollTrack sets the track explicitly.

An activeIndex that names a disabled tab

The tablist shows the first enabled tab rather than nothing — but activeIndex keeps the value it was given, so the bound value and the tab on screen disagree. Bind indexes of enabled tabs.

Eager or lazy content

Content written directly inside a <gog-tab> renders eagerly and is merely hidden while inactive — right for cheap content, because scroll position, unsubmitted input and any state the DOM holds survive a switch. Wrap it in an <ng-template gogTabContent> and it is built on first activation and kept alive after. Which you get is decided by whether that template is present — there is no lazy input to keep in sync with it.

Eager and lazy, side by side

Type in the first tab, switch away and back: the text is still there. The third tab's content is not in the DOM until you open it.

Accessibility

The headers form a real tablist, and each panel is a tabpanel labelled by its header.

  • Name — set ariaLabel on <gog-tabs> to say what the tabs switch between ("Account settings"); each tab is named by its label. Only the app knows that name, so an unnamed tablist logs one console.warn per page in dev mode , never in production.
  • Keyboard — one tab stop for the whole row. The arrow keys move between tabs following orientation — a horizontal tablist leaves ArrowDown to the page — and Home / End jump to the ends. Activation follows focus, the automatic variant of the ARIA tabs pattern. Disabled tabs are skipped rather than merely unclickable.
  • Panels — each panel is focusable, so tabbing out of the tablist lands in the content.

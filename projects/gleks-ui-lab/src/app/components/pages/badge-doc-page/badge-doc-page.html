gogBadge

Badge

A count or status dot pinned to the corner of another element. A directive, not a component — it decorates a button, an icon or an avatar without wrapping it, so the host's own layout is untouched.

Overview

Import the directive and put it on the element to decorate.

Basic usage:

Examples

Content and variants

Five kinds of content in the four semantic colours, which are the names gog-tag takes. danger is the default, the colour of a count someone should look at. A number over badgeMax (99) prints as 99+; a word is left alone, since capping only means something for a count. badgeDot drops the text for "something changed here", with no number to give.

It never renders "0"

A badge reading 0 is the defining bug of this component class, so it is not reachable: 0, null and '' render nothing at all, and a call site can bind a count straight from state without an @if. Step the count down to zero. badgeHidden is the other way to take the badge away — the count underneath is kept, so it comes back as it was. Neither changes the host's size, because the badge was never part of its layout.

Positions

The four corners, as logical positions: end is the right-hand corner here and the left-hand one in a right-to-left page. The badge overhangs the corner by --gog-badge-offset, so leave that much room around a badged element in a tight row.

Hosts

A directive, so it decorates what is already there rather than wrapping it: a gog-button, a native button, a link styled with gogButton, or any element — the host only gains position: relative to hold the badge. An inline element has to be made a box (inline-flex on the avatar) so the corner is its corner.

Dot

A dot shows even with no value bound. It has no text of its own, so give it badgeAriaLabel — and put it on the control it belongs to, not on that control's icon: a gog-icon is aria-hidden, so a badge inside one is never announced.

Caps

Counts above badgeMax (99 by default) render as N+, so a badge never grows without limit. Non-numeric content passes through untouched, so a word works as a label.

Accessibility

badgeAriaLabel replaces the visible badge text for assistive tech — the visible badge becomes aria-hidden and your wording is read instead. A dot has no text of its own, so it needs badgeAriaLabel to be announced at all. What the wording becomes depends on the host:

  • A focusable host — <button gogBadge>, a[gogButton] — gets it as part of its name: "Inbox 12 unread".
  • A host whose focusable element is inside it, like gog-button, gets it as a description of that element, through aria-describedby: "Inbox, button, 12 unread" . Before 21.15.0 the badge landed beside the inner button rather than on it, and Tab said only "Inbox, button".
  • A host with nothing focusable gets plain text after its own — and inside a decorative gog-icon, which is aria-hidden, nothing at all. Put the badge on the control the count belongs to.
  • Wording — without badgeAriaLabel a screen reader hears the bare number, "Inbox 12", which is often enough. Give the wording when the number alone is ambiguous — "12 unread", "3 failed checks" — and keep it in step with the count, as the "0" example does.
  • Keyboard — none of its own. The badge is never a tab stop; the host keeps its own keyboard behaviour unchanged.

The badge node is created in the browser only. That is deliberate: a node the server renders but the client's hydration walk knows nothing about is an NG0500 mismatch, so it costs one frame after hydration and buys a directive that is safe in an SSR app.

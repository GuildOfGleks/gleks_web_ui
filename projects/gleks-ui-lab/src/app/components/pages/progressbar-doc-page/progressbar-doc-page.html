gog-progressbar

Progress Bar

A horizontal progress indicator in three modes — determinate, indeterminate and buffer — five sizes and the library's semantic color set.

Examples

Modes and sizes

determinate fills to value; buffer adds a lighter tier behind it for what has been fetched but not reached — a streaming or preload position; indeterminate sweeps a segment for work whose length is not known. Under prefers-reduced-motion the sweep stops and the bar is drawn striped instead, which still reads as "working". Five thickness steps, from a hairline to a chunky bar.

Variants

accent is the default — progress is usually just "the app is working", which is not one of the four status hues. GogProgressbarVariant is an alias of GogSeverity, so these are the same five names gog-button's severity takes.

Showing the value

Off by default, because a bar usually sits under a label that already says what it measures. On, the percentage prints beside the track in tabular figures, so the bar does not shift as the number changes. It is never shown in indeterminate mode, which has no number.

A value that moves, and one that overshoots

value and buffer are percentages, clamped to 0–100 rather than trusted: a bar driven straight from loaded / total overshoots on the last chunk often enough. Step past either end — the bar stops, and aria-valuenow with it, while the number you passed is kept as you passed it. The fill moves with a short transition, which reduced motion turns off.

Where the fill ends

With showValue off, the boundary between fill and track is the value, and WCAG 1.4.11 asks 3:1 of the part of a graphic that carries its meaning. Colour alone cannot always carry it: 51 of the 55 shipped fill/track combinations are below 3:1, because the five fills straddle mid-luminance and no single track colour clears all of them in any theme but primeng.

The edge marker

--gog-progressbar-edge-width is 0px by default . Set it to 1px — on :root, or on one bar — and two hairlines mark where the fill ends, and in buffer mode where the buffer ends: the theme's ink outermost against the track, the surface colour just inside the fill. Whichever tone a fill sits close to, the other one reads; the worst case across the eleven themes is 3.25:1. The grayscale columns are the same bars with hue taken away. The tones are --gog-progressbar-edge-color / -edge-backing-color, and they flip end under dir="rtl". Where the value has to be readable without colour, this or showValue is the consumer's call.

Accessibility

role="progressbar" on the host, with the value stated as a number and as text, and no number at all when there is none.

  • Value — aria-valuemin / aria-valuemax, and in determinate and buffer mode aria-valuenow plus a readable aria-valuetext. buffer reports only value: the buffered tier is a picture, not a second number anyone needs read out.
  • Indeterminate leaves aria-valuenow out — that absence is what tells a screen reader the length is unknown; reporting 0 would announce "0 percent" for as long as it ran.
  • Keyboard — none. A progress bar is not focusable.

Every bar needs a name

ariaLabel is empty by default, and a bar with no name is announced as "progress bar, 62 percent" — of what, nobody says. Pass ariaLabel, or, when a visible label already sits beside the bar, point at it with aria-labelledby written on the host: the component binds none of its own, so yours reaches the element with the role. A <label for> cannot do it — a progress bar is not a form field.

gog-menu

Menu

A command menu opened from a button you own. [gogMenuTrigger] goes on your button, gogMenuItem on your items — so an item can carry an icon, a label and a shortcut hint without an input per piece. A closed menu renders nothing at all, so its commands are not in the accessibility tree until it opens.

Overview

Import the component and the two directives. The trigger is a directive rather than a component of its own — the same decision as [gogButton] — because a menu button is usually an icon button you have already styled, and a wrapper would fight that.

There is no appendToBody. The panel always renders into <body> and is placed from the trigger's measured rect, so a menu inside gog-scroll, gog-table or any overflow: hidden ancestor is not clipped and needs nothing configured. It also takes the --gog-dropdown-z its trigger inherits, so a menu opened inside a gog-dialog stacks above the dialog rather than behind it.

Keyboard

The WAI-ARIA menu button pattern, in full. This is most of what the component is for — none of it is visible in a screenshot, and it is the part a hand-rolled dropdown almost always leaves out. Open the demo above and try it.

Examples

Row actions

What the component was built for: an icon button per row. The library created this gap itself — 21.4.0 added the more-horizontal / more-vertical icons and a table built for row actions, with nothing to open with them. The table wraps itself in a gog-scroll and the panel still escapes it, which is why the menu always renders into <body> rather than offering a mode to get this wrong in.

Disabled items

An item is your own <button>, so you disable it the way you disable a button: the native disabled attribute, static or bound — there is no input for it. A disabled item stays in the list rather than disappearing, since removing it would shift every other item under the pointer; the arrow keys step over it, and clicking it does nothing. With Locked on, the second menu leaves only Open reachable, and ↓ from it wraps back to itself instead of landing on a dead command.

A long menu scrolls itself

A panel taller than the room between its trigger and the viewport edge scrolls with gog-scroll — the same thin, auto-hiding scroller as everywhere else in the package, with overscrollBehavior="contain" so a wheel at the end of the list does not scroll the page behind it. Arrowing past the last visible item scrolls it into view. Shrink the window and reopen this menu to see it.

Known defect in {{ libraryVersion }}: --gog-menu-max-height does not cap the panel. The component measures the space available and writes that height onto the panel as an inline max-height, which beats the stylesheet rule the token feeds — so the token applies only when it happens to be larger than the space, i.e. never usefully. Setting it to 150px on a page with 500px of room changes nothing. The panel still scrolls; what you cannot currently do is choose the height it starts scrolling at.

Direction

direction is auto by default: the panel drops down whenever it fits and flips up only when it cannot. Force it with up or down.

Directives

Selector Goes on Description
[gogMenuTrigger] your own button Takes the menu to open — <gog-menu #rowMenu> plus [gogMenuTrigger]="rowMenu". Required.
gogMenuItem your own buttons, inside the menu Marks an item so the panel can find it for roving focus. No inputs — an item's label, icon and disabled state are all just the button's own.

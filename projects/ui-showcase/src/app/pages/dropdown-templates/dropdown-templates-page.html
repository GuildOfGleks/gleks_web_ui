gogDropdownOption — the inside of one row

The slot replaces the row's content, never the row. The host still renders the option element around it — a <button role="option"> in the two listbox controls, a <div> in gog-autocomplete, which is a combobox and keeps focus in its field — with its padding, its hover and selected states, its check mark and every ARIA attribute. That is why a custom row costs no accessibility, and why it must not contain anything focusable: a button inside a button is invalid, and a tab stop inside a list that has exactly one is unreachable.

gogDropdownChevron — the glyph, not the slot it sits in

The template is rendered through gog-icon, so it inherits the icon box the host reserves and lines up with whatever was there before. The wrapper stays aria-hidden, which is what makes any markup put here decorative by construction.

gogDropdownOption works in all three. gogDropdownChevron works in two: gog-autocomplete has no chevron at all — its trigger is a text field, so there is nothing for the template to replace and it is silently dropped. The directive is still accepted there, because all three inherit it from the same base; the backlog carries that.

the open state, which the two hosts hand over differently

Open the two fields below and watch the glyph. gog-multiselect still turns it — the rotation lives on the wrapper and follows the panel whatever is inside. gog-select stops turning it: its rotation class is applied only while there is no custom template, on the reasoning that an arbitrary glyph is not necessarily a chevron and turning it upside down may be wrong. The template gets no context either, so in a select the open state is yours to draw — through .gog-select--open in your own stylesheet. Two answers to one question, and the backlog has the entry.

why every example here writes $any

GogDropdownOptionContext<TOption> is generic and the directive declares no input, so under strictTemplates nothing in a template can infer the parameter: it stays unknown, and the first property read off let-option fails with TS2571. let-label is unaffected — it is typed string whatever TOption turns out to be — so a row that only decorates the label needs no cast at all. That is the cheapest way out until the directive gains a type token; the backlog carries the fix, built and measured.

Open the first two fields and compare the attribute lines: a custom row reports exactly what a default one does. The third reads the chevron's wrapper, which is aria-hidden whether or not a template fills it — so a glyph put there is never announced, and an icon carrying a title would not be either. Nothing focusable belongs in a row: the list is one tab stop, and a button inside an option is either unreachable or steals the press the option needed.

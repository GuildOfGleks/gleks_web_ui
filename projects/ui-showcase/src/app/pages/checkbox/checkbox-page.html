size × state

indeterminate and checked are separate inputs and the dash wins while both are set: it is the "some of them" state, and a row that is partly on cannot also be on. The three lengths behind each column — the box, the glyph and the label — come from the shared --gog-control-checkbox-* scale that gog-radio-group reads too, which is why a checkbox and a radio line up on a form. gog-toggle is not on it — a switch has its own --gog-toggle-<size>-* scale and borrows only the padding.

the label, and the field with none

The whole control is a <label> wrapped around a real <input type="checkbox">, so the text is the accessible name — there is no for to wire up, pressing the text toggles the box, and a form submits it the way it submits any checkbox. ariaLabel is for the case with no visible text, which is the only case it applies to.

fullWidth

Off by default: a checkbox is as wide as its label, so a row of them reads as a row. Turned on, it fills its container — which is what puts the box at one edge of a settings row and leaves the rest of the line clickable.

gogCheckboxIcon — the tick, not the box

The slot replaces the glyph inside the box, rendered through gog-icon so it inherits the size the scale gave it. The box, its border, its fill and every state stay the component's. It is the checked glyph only: the indeterminate dash is drawn by the stylesheet and a template does not reach it, which the third checkbox below shows.

This is the one thing about this component worth reading before using it. A native checkbox resolves indeterminate on the first click; here the dash is drawn from the input, so a press changes checked and leaves indeterminate exactly as it was. Press the second checkbox below a few times: its checked flips under the dash and nothing visible moves. That is not a bug to work around — it is what lets a parent row be driven from its children rather than from its own presses — but it does mean the state is yours to compute.

One detail that only shows up if you read the element rather than the component: the browser clears the native indeterminate property on a press. The dash is drawn from the input and not from the property, so the screen stays right — but until 21.15.0 the element was left reporting false under a visible dash, which is what a consumer's input:indeterminate rule, a test or an automation script would have read. The change handler writes the input's own value back now, so the two agree.

formControl, and the error a checkbox does not draw

Validators.requiredTrue is what "you must tick this" is written as. Note what is missing from the API table: there is no errorMessage and no errorDisplay — a checkbox has no error line of its own, so the message belongs to whatever the form renders around it. Disabling through the form works the same as the input: both end up in disabled on the native element.
